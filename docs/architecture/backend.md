# Backend architecture

The Java side of the bundle: how a request becomes entities, and the contracts every Creator, resource command and workflow adapter must keep. Start with [`overview.md`](overview.md) for the big picture. Coding rules for this area are in [`.claude/rules/backend-java.md`](../../.claude/rules/backend-java.md); Liferay API facts are in [`reference/liferay-dxp-api.md`](../reference/liferay-dxp-api.md).

## Layers

| Layer | Package | Responsibility |
|---|---|---|
| Resource command | `portlet.actions` | Parse the request, validate user input, build value objects, call the Creator (or UseCase), serialize the result |
| UseCase (optional) | `service.usecase` | Call a Creator, then do read-only enrichment that must not fail the batch |
| Creator | `service` | Create N entities, one transaction each, and return `BatchResult<T>` |
| Value objects | `service` | `BatchSpec`, `*BatchSpec`, `EmailDomain`, `AssetTagNames`, `RoleType`, `SiteMembershipType` |
| Workflow adapter | `workflow.adapter.*` | Expose a Creator as a workflow operation |
| Data list provider | `service.datalist` | Serve dropdown options through `/ldf/data` |

## Input boundary policy

Every input falls into exactly one category, and each category has exactly one strategy. Mixing them causes either silent UX bugs or flaky tests.

| Input | Example | Strategy |
|---|---|---|
| User-supplied free text | `baseName` typed in a form | **Reject** at the resource command or Creator boundary with a clear error. Never rewrite it — a user who types `山田` must not silently get users named `1, 2, 3`. |
| Externally generated data | Datafaker names, RNG output | **Sanitize** (e.g. `ScreenNameSanitizer`), because nobody can fix the input. |
| A choice from a closed set handed to an external generator | `locale` dropdown passed to Datafaker | A deterministic **fallback** to the generator's default is acceptable; the user's intent is preserved at the category level. Not a licence to rewrite free text. |

Notes:

- **Workflow JSON is user input.** A sample template reaches `UserCreator` through the same path as a form submission, so template values must pass the same validation (for example, a non-faker user `baseName` must match `^[a-z0-9._-]+$` after lowercasing — use `sample-workflow-user`, not `Sample Workflow User`).
- **`AssetTagNames` is the one normalizing parser for tags.** `AssetTagNames.of(String)` lowercases, trims, splits on commas, drops empty tokens and de-duplicates in first-seen order; blank input is `AssetTagNames.EMPTY`. Creators that attach tags call `ServiceContext.setAssetTagNames(tags.toArray())` only when `!tags.isEmpty()`. Liferay-side behaviour: [liferay-dxp-api](../reference/liferay-dxp-api.md#servicecontextsetassettagnames--auto-create-and-group-scope).
- **Validation runs outside the transaction.** Throw validation exceptions before the first `BatchTransaction.run(...)`; no transaction has started, so nothing needs rolling back, and the resource command's `catch (Throwable)` turns the exception into `{success: false, error}`.

## Batch response contract

Every batch Creator returns `BatchResult<T>` (record in `service`), and every entry point serializes it as:

```
{success, count, requested, skipped, items, error?}
```

| Field | Meaning |
|---|---|
| `success` | **Strict**: `count == requested`. Requesting 10 and creating 3 is a failure, not a partial success. |
| `count` | Entities actually created. |
| `requested` | Entities asked for. Always present. |
| `skipped` | Entities deliberately skipped by a catch-and-continue loop. Always present. |
| `items` | The created entities. The key is always `items` — never `users`, `roles`, … |
| `error` | Present **if and only if** `success == false`. |

`BatchResult`'s canonical constructor enforces the invariants, so they cannot be broken by a careless edit:

- `requested > 0`; `count >= 0`; `skipped >= 0`
- `success == false` requires a non-blank `error`
- `success == true` requires `count == requested`
- `items` is defensively copied

Construct results with the factories `BatchResult.success(requested, items, skipped)` and `BatchResult.failure(requested, items, skipped, error)`, which derive `count` from `items.size()`. A Creator with a catch-and-continue loop tracks `skipped` itself and passes it in; downstream code never reconstructs it.

The single exception is `WebContentCreator`: it batches across several sites and returns one item per site (`WebContentPerSiteResult {groupId, siteName, created, failed, error}`) so the UI can show "site A succeeded, site B failed". Its `count` is the total number of articles, not `items.size()`, so it uses the canonical constructor. `WebContentPerSiteResult` mirrors the invariant per site: `failed > 0` ⇔ `error` is set.

In dummy mode (`createContentsType: 1`) article titles are generated by Datafaker; `baseName` is not used as the title. Tests that need to find the created articles cannot filter on `baseName` — order by `modifiedDate` descending and take the newest N, or use another deterministic field.

Serialization has exactly one implementation per entry point:

- Resource command: `ResourceCommandUtil.toJson(result, item -> …)` — writes `error` only on failure.
- Workflow adapter: `WorkflowResultNormalizer.normalize(result, item -> Map.of(…))` — public so adapters in sibling packages can use it.

Failure messages always go in the field `error` (`ResourceCommandUtil.setErrorResponse` writes it). The frontend reads no other name.

History: [ADR-0009](../adr/0009-unified-batch-result.md).

## Creators

Each `*Creator` wraps the per-entity work in `BatchTransaction.run(() -> { … })`:

- `BatchTransaction` (in `utils`) owns the transaction configuration (`Propagation.REQUIRED`, rollback on `Exception`). Creators never declare their own `TransactionConfig` or call `TransactionInvokerUtil` directly, so cross-cutting changes happen in one place.
- One transaction per entity means a failure in the middle of a batch does not roll back the entities already created.
- `create(...)` declares `throws Throwable` because `BatchTransaction.run` does; resource commands catch `Throwable`. Rationale and trade-offs: [ADR-0001 §7](../adr/0001-integration-test-architecture.md#7-creator-services-declare-throws-throwable).

### Parameters: `BatchSpec` and `*BatchSpec`

- `BatchSpec(count, baseName)` validates both in its compact constructor. `ResourceCommandUtil.parseBatchSpec(data)` reads `count` and `baseName` from the payload — so any form whose command uses it must include a `baseName` field.
- **Count cap.** `count` must be between 1 and `BatchSpec.MAX_COUNT` (1000) per request — per workflow step. Larger values are rejected with an error that states the limit, never truncated. `BatchSpec.validateCount` is the single check: the compact constructor, `ResourceCommandUtil.validateCount`, the workflow `WorkflowParameterValues` helpers and `WorkflowInputValidator.requireCount` all call it. Web content `count` is per site, so `WebContentBatchSpec` also rejects `count × groupIds.length` above `BatchSpec.MAX_COUNT`. Decision: [ADR-0010](../adr/0010-mcp-via-liferay-mcp-server.md).
- When a Creator needs more than about five parameters, they move into a `*BatchSpec` record (`UserBatchSpec`, `WebContentBatchSpec`, `MBReplyBatchSpec`, …) that composes `BatchSpec batch`. Its compact constructor normalizes nullable inputs to their defaults (e.g. `null` tags → `AssetTagNames.EMPTY`), so callers need no null checks. Creators with few parameters (`OrganizationCreator`, `RoleCreator`) keep raw parameters plus `BatchSpec`.
- `EmailDomain.of(raw)` rejects blanks and `@`, and defaults to `liferay.com`. `RoleType` and `SiteMembershipType` map UI strings to Liferay constants.

## Resource commands

The portlet's Control Panel permission governs access to its resource commands. `/ldf/company` additionally requires the request's permission checker to be an omniadmin, matching DXP's Virtual Instances app: a company administrator of a secondary instance must not create virtual instances. `CompanyResourceCommandTest` covers the check. A denial returns the template's usual `{success:false, error}` JSON with HTTP 200, unlike the REST path's HTTP 403. REST and MCP authorization is defined in [Workflow API authentication](../reference/workflow-api.md#authentication).

Every resource command except `DocumentUploadResourceCommand` (multipart upload) delegates to the template:

```java
PortletJsonCommandTemplate.serveJsonWithProgress(
	resourceRequest, resourceResponse, _portal, _log,
	"Failed to create <entities>",
	(context, data, responseJson) -> {
		BatchSpec batchSpec = ResourceCommandUtil.parseBatchSpec(data);
		// parse and validate the rest of data, then call the Creator
		return ResourceCommandUtil.toJson(result, item -> item.toJSONObject());
	});
```

The template owns request parsing, the `ProgressManager` lifecycle, routing `IllegalArgumentException` and `Throwable` to `setErrorResponse`, and writing the JSON. `PortletJsonCommandContext` provides `getUserId()`, `getCompanyId()` and `getProgressCallback()`. Each command keeps its own `_log` and `_portal` fields because it passes them to the template.

Validation helpers in `ResourceCommandUtil`: `validateCount`, `validatePositiveId(id, field)`, `validateNotEmpty(value, field)`. Use `validatePositiveId` for every "must be > 0" id; write `if (id < 0)` only where `0` is a meaningful sentinel (e.g. `categoryId = 0` is the root message-board category).

`WcmResourceCommand` returns its own JSON (`ok`, `totalRequested`, `totalCreated`, `perSite`) instead of `toJson`, and still writes `error` whenever `result.success()` is false.

A new command is only reachable from the UI and the test client after it is registered in `view.jsp` — see [adding an entity](../guides/adding-an-entity.md).

## UseCases: non-fatal enrichment

`UserCreateUseCase` and `SiteCreateUseCase` call their Creator and then look up extra data (layout-set prototype UUIDs) for a richer item DTO. Those lookups run after the entities are committed, so they must not fail the batch: they catch `Exception`, log at WARN with the exception, and return `null`/`0L` for the optional fields.

This pattern is only for read-only enrichment after the Creator call. It never applies inside a Creator's per-entity loop. And a UseCase is only justified when such a secondary call exists — if the Creator returns a Liferay model whose getters already expose every needed field, map them in the command's `toJson` lambda.

## Data list providers

Dropdown options come from `DataListProvider` implementations under `service/datalist/`, collected by `DataListResourceCommand` (`/ldf/data`) through a `MULTIPLE`/`DYNAMIC` reference. Adding a source is one new `@Component(service = DataListProvider.class)`; the command does not change.

The interface has two `getOptions` overloads. The default 3-argument one (`companyId, type, HttpServletRequest`) drops the request and calls the 2-argument one, so a provider that needs request parameters (such as `groupId`) must override the 3-argument overload. Examples: `VocabulariesDataListProvider`, `MBCategoriesDataListProvider`.

## Workflow adapters

Each operation (`site.create`, `user.create`, …) is a `WorkflowOperationAdapter` OSGi service under `workflow/adapter/{core,content,taxonomy,messageboards}`. An adapter reads its parameters with `WorkflowParameterValues` (`optional*` helpers for optional parameters), builds the same `*BatchSpec` the resource command builds, calls the Creator, and returns `WorkflowResultNormalizer.normalize(...)`.

Some adapters build their `*BatchSpec` in a `*Request` helper in the same package (e.g. `WebContentCreateRequest`). When a `*BatchSpec` gains a field, update both the adapter and the helper.

Operation-level behaviour and the field parity table: [`reference/workflow-api.md`](../reference/workflow-api.md).

## Test-only components

`BasicAuthTestSetup` and `SAPTestSetup` ship in the production JAR but stay inactive unless a matching `.config` is deployed (`ConfigurationPolicy.REQUIRE`); the test image deploys it from `configs/common/osgi/configs/`. The pattern and why each annotation is needed: [dxp-runtime-config](../reference/dxp-runtime-config.md#test-only-osgi-components).
